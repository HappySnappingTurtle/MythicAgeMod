# MythicAgeMod 核心目标重定义与全面审计

> 日期：2026-10-11
> 性质：重构前的全面重审。不以既有代码和文档为前提，所有结论都经代码或运行证据核实。
> 依据：玩法系统代码审计、生物/资源/世界生成审计、设计文档考古、编译验证、崩溃报告。

---

## 1. 核心目标（重新确认）

**一句话：** 把《神话时代》的"文明差异化恩宠（Favor）→ 神力"循环搬进 Minecraft 生存。玩家在世界中找到神话文明的神殿，用该文明独有的方式积累恩宠（现名"神力证明"），再把恩宠换成神力，施放改变世界的神迹。

**灵魂：** 五个文明"恩宠来源不同"。
- 希腊：信徒朝圣
- 埃及：供奉神像（纪念碑）
- 北欧：战斗
- 中华：人口与劳作
- 亚特兰蒂斯：待定

这是同类神话 mod（如 Ice and Fire）没有的维度，也是本项目唯一真正原创的资产。

**外壳，都应服务于上面的循环：** 神话生物、神殿建筑、圣物、美术、粒子、音效。

**现状偏离：** 2026-06 以后的投入主要流向两处：生物美术审批流程（64 个 Python 脚本、30 来份门禁/台账文档、136MB 预览图）和单个资产打磨（行走树根系、Pegasus/Hydra V3→V6）。核心循环本身在生存模式中**走不通**，见第 3 节。

## 3. 核心循环在生存模式中的真实状态

| 文明 | 设计上的恩宠来源 | 代码路径 | 生存可用？ | 断点 |
|---|---|---|---|---|
| 希腊 | 守护者附近的希腊村民 → 存入神像基座 | `CustomTempleGuardianEntity.tick` → `CertificateGenerationManager.generateCertificatesForTemple` | ❌ | 世界生成的神殿没有守护者；没有希腊神殿生成书 |
| 埃及 | 神像台供奉神像，周期产出 | `EgyptianStatuePedestalBlockEntity.tick` | ❌ | 7 种神像物品无任何获取途径；取下神像返还金锭占位；`GodPowerCertificateManager.tickEgyptianStatues` 是重复的第二条产出路径 |
| 北欧 | 击杀掉落 | `ModCombatEvents` → `handleNordicKill` | ⚠️ 能拿到，没处花 | 北欧守护者只能用法术书生成，而这本书又只能向守护者买 |
| 中华 | 人口 / 劳作 / 交易 | `GodPowerCertificateManager.tickChinesePopulation`、`ChineseCertificateManager` | ❌ | **所有村民都被默认设为希腊文明**（`worldgen/VillageManager.java:203-206`），中华村民永远不存在 |
| 亚特兰蒂斯 | 16 海晶碎片换 1 证明 | `CustomTempleGuardianEntity.java:310` | ❌ | 守护者无法自然生成 |

**生存中实际能拿到的内容**，只有北欧证明，以及战利品箱注入的 4 本希腊法术书和 5 件圣物（`event/ModLootTableModifiers.java`）。其余全部只能从创造物品栏拿。

## 4. 问题清单

### P0：阻断与崩溃
1. **核心循环断裂**，见第 3 节。其中世界生成钩子 `VillageGenerationEventHandler.onStructureGenerated` 无人调用，整条村庄文明化链路（`VillageManager`、`MythicVillageProcessor` 486 行、`BiomeCivilizationMapper`）都是死代码。
2. **版本管理失控**：169/246 个 Java 文件未入 git，无法回溯，也无法回滚。
3. **独立服务器崩溃风险**：`entity/CustomTempleGuardianEntity.java:155` 在通用代码里直接 `new CustomTempleGuardianTradeScreen` / `MinecraftClient`。
4. **未修复的崩溃**：2026-06-14 的 `Accessing LegacyRandomSource from multiple threads`（`run/crash-reports/`），来源未定位。
5. **正式包中朝圣 AI 失效**：`mixin/VillagerAIEnhancementMixin.java:79` 反射 `getDeclaredField("goalSelector")`，生产环境使用 intermediary 名，必定抛出 `NoSuchFieldException`。

### P1：功能损坏
6. **丰饶祭坛永不产出**：校验要求 `GOLD_H/GOLD_V`（`AbundanceAltarCoreBlockEntity.java:117,238`），法术实际放置的是 `GOLD_CORNER/EW/NS`（`PlentySpell.java:111-117`）。
7. **诅咒**对 10 格内所有非玩家生物直接 `discard()`，包括村民、守护者、Boss（`CurseSpell.java:26-44`）。
8. **闪电风暴**对 50 格内所有非玩家生物造成 `Float.MAX_VALUE` 伤害，冷却比持续时间短，可以叠加（`util/LightningStormManager.java:180-199`）。
9. **地震**每轮破坏约 2.17 万方块并 90% 掉落，持续 12 轮，可产生数万掉落物，严重卡服（`util/EarthquakeManager.java:181-205`）。
10. **冥府军团**召唤的是敌对原版骷髅，会攻击施法者（`UnderworldArmySpell.java:21-33`）。
11. **圣物**：
    - 手持的再生效果每 tick 被重置，永远不回血；丰饶角给的是无限饱和。
    - 神殿层效果是占位实现（`RelicPedestalBlockEntity.java:117-122`，`RelicItem.java:340` TODO）。
12. **神像兑换是半成品**：`StatueBlock.handleExchange` 只打印信息，既不扣证明也不发书（`block/StatueBlock.java:183-217`）。
13. **亚特兰蒂斯海洋生物会溺水**：它们刷在海里，却没有水生呼吸和游泳导航。
14. **Hydra 贴图错乱**：模型声明 256×256 贴图，实际文件是 128×128（`HydraModel.java:119`）。
15. **守护者交易表**用 `Map<ItemStack,ItemStack>`，按 identity 哈希，顺序随机；`hasInitializedTrades` 被持久化，老存档永远拿不到新交易。
16. 所有法术都不检查 `mobGriefing`、出生点保护或任何开关（全仓库对 `GameRules` 的引用为 0）。

### P2：架构与工程债
17. **重复系统**：
    - 两套守护者：`TempleGuardianEntity` 732 行，`CustomTempleGuardianEntity` 763 行，共 11 个 EntityType。
    - 埃及有两条产出路径，中华有三条。
    - 三处各硬编码一份价格表。
    - 文明 switch 复制了 5 份以上。
18. **静态可变状态**：
    - `GodPowerTaskScheduler.TASKS` 跨存档泄漏、不持久化，执行时会出现并发修改。
    - `VillageManager.villageTypeMap` 静态，从不清空。
    - 证明冷却 key 带原始 Y 坐标，map 无限增长。
19. **性能**：
    - 希腊扫描神像基座，每次约 27 万方块。
    - 中华用整个世界边界大小的 Box 查实体。
    - 圣物每 tick 调用 `addStatusEffect`。
20. **冷却有两套数值**：`AbstractSpell.defaultCooldown` 是死字段，实际生效的是 `ModItems.cooldownTicks`，两者不一致。
21. **调试代码混在 main 中**：
    - `validation/ValidationCommand.java`（1190 行）无条件注册，会改写真实存档的固定坐标地形。
    - `client/visual/VisualProbeServer.java`（832 行）是可执行任意命令的本地 HTTP 服务。
22. **`VillageManager.java:166` 在服务端主线程 `Thread.sleep(1000)`**：目前是死代码，一旦接线就会卡死服务器。
23. **生物同质化**：
    - 非希腊的 20 个生物是同一个 `tick → 距离判定 → 瞬发伤害 + buff` 模板，最远 12 格，无弹道、无前摇。
    - 五个 `*MythEntity` 基类除音调常量外逐字相同。
    - 生物不掉落任何 mod 物品，与核心循环无关。
24. **数据包四件套为零**；三语言键不一致（en 783 / zh 816 / ja 753）；缺 `icon.png`；`fabric.mod.json` 仍是模板信息。
25. **`ModConfig` 全是 `static final` 常量**，不是真正的配置。
26. **文档互相矛盾**：
    - 希腊证明来源有 4 种说法；README 和 CHANGELOG 写的"矿物兑换"在代码中不存在。
    - 埃及的档位和周期、中华产出、北欧掉率、法术总数（52/55/56）、Hydra 头数（5/9）各处都不一致。

## 5. 资产处置判定（保留 / 重写 / 删除）

| 模块 | 判定 | 理由 |
|---|---|---|
| SpellRegistry + AbstractSpell 架构 | **保留**，小改 | 方向正确；需统一冷却和目标计算，并加入施法成本 |
| 网络包 + 自定义交易 GUI | **保留**，重写数据模型 | 交易表改为有序 List 和数据驱动 |
| `CustomTempleGuardianEntity` | **重写**（拆分） | 763 行混合了 AI、交易、网络、NBT 和 GUI |
| `TempleGuardianEntity` 旧版全套 | **删除** | 已被取代 |
| `StatueBlock` 兑换、`TempleBlock` | **删除或合并** | 半成品，结构中也不使用 |
| 三个证明管理器 | **重写**为单一 `FavorService` | 消除重复路径，持久化到 `PersistentState` |
| 村庄文明化链路（`VillageManager` / `MythicVillageProcessor` / `BiomeCivilizationMapper`） | **重写** | 死代码，且设计有误：静态 map、sleep |
| 朝圣 Mixin | **重写** | 反射在生产环境失效；应改用 accessor mixin 或 Brain 任务 |
| 56 个法术实现 | **逐个评审**：保留精品，修复危险项，砍掉凑数项 | 诅咒、闪电风暴、地震必须改 |
| 15 个神殿 NBT + structure_set | **保留**，补守护者和 processor | 骨架可用 |
| 30 个神话生物 | **保留注册与模型**；**玩法重定位** | 要接入循环：作为召唤单位、守卫或掉落来源 |
| `ValidationCommand` / `VisualProbeServer` | **移出 main**，改为 dev 源集或 GameTest | 不应随正式 jar 发布 |
| `tools/` 64 个 Python 门禁脚本 | **归档** | 只保留 bbmodel 同步等真正有用的 2–3 个 |
| `docs/项目管理` 的 30 来份流程文档、`_备份` 副本 | **归档** | 由一份 `STATUS.md` 和一份权威玩法规格取代 |
| `docs/preview_assets`（136MB） | **移出仓库** | 由生成脚本重新产出，不入版本控制 |

## 6. 需要用户拍板的设计问题

> **2026-10-11 用户决议**（以 `TODOList.md` 中「已冻结的核心决策」为准）：
> 1. 施法不消耗恩宠。恩宠用于在守护者处兑换神力卷轴或道具，这些是一次性消耗品。
> 2. 恩宠存玩家数据，按文明分槽。
> 3. 不设宣誓或主神，一个存档就能体验全部文明。
> 4. 先跑通一个文明（希腊），再做其余文明。
> 5. 生物分为召唤单位、野外怪物和 Boss；圣物（增益 buff）保留。
> 6. 版本与加载器由开发方综合评估后选定：**NeoForge + Minecraft 1.21.1**，先只做单一加载器（评估见第 8 节）。初稿曾选 Fabric 26.1.2，已作废。
>
> 下面是原始问题，保留作记录。

1. **恩宠是否在施法时消耗？**
   现状是"买书一次，之后无限施法"，证明很快失去意义。《神话时代》原作是施法消耗恩宠并带冷却。
2. **恩宠的载体是物品还是玩家数据？**
   物品可以交易、丢失、存箱；玩家数据像经验条一样按文明分槽，更接近 AoM。
3. **玩家是否"宣誓信奉"一个文明（主神）？**
   AoM 的核心结构是"选主神 → 晋升时代 → 选小神 → 解锁神力"。引入这个结构后，玩家一次只深耕一个文明，范围和平衡也更可控。
4. **范围：希腊垂直切片先行，还是五文明并行？**
5. **神话生物的定位：** 野外刷怪、恩宠召唤的神话单位（更贴近 AoM），还是神殿守卫或 Boss？
6. **MC 版本：** 留在 1.20.1，还是借重构迁移到更新版本？

## 8. 平台选型评估（2026-10-11）

### 8.1 市场数据（Modrinth API，2026-10-11 采集）

| 版本 | 模组 Fabric | 模组 NeoForge | 整合包 Fabric | 整合包 NeoForge | mobs/adventure 分类 Fabric | mobs/adventure 分类 NeoForge |
|---|---|---|---|---|---|---|
| 1.20.1 | 17,653 | 5,076（Forge 25,147） | 4,303 | 263（Forge 3,029） | – | – |
| **1.21.1** | 19,504 | **21,259** | 3,056 | **2,152** | 5,616 | **7,441** |
| 1.21.11 | 17,830 | 8,089 | 2,854 | 83 | – | – |
| 26.1.2 | 13,002 | 7,944 | 1,331 | 66 | 3,498 | 2,725 |
| 26.3（最新） | 7,262 | 4,054 | 478 | 11 | 1,964 | 1,428 |

**同类内容模组的选择：**
- Modrinth 上 mobs 分类按下载量排序，L_Ender's Cataclysm、Mowzie's Mobs、Touhou Little Maid、Guard Villagers 都只做 Forge/NeoForge。
- Cataclysm、Mowzie's、Cobblemon、The Aether、Deeper and Darker 都停在 1.21.1，尚未上 26.x。

**数据局限：**
- 只有 Modrinth 数据，Modrinth 本身偏 Fabric。
- CurseForge 没有公开 API，无法核实，但它通常更偏 Forge/NeoForge。
- 国内整合包圈的倾向未经数据核实。

### 8.2 本项目需求对照

| 需求 | NeoForge 1.21.1 | Fabric 1.21.1 | Fabric 26.1.2 |
|---|---|---|---|
| 实体动画（GeckoLib） | ✅ | ✅ | ✅ |
| 圣物饰品槽 | ✅ Curios（事实标准） | ⚠️ Trinkets / Accessories | ❌ 两者都没有 26.x 版本 |
| 玩家恩宠数据 | ✅ Data Attachments | ✅ Attachment API | ✅ |
| 生物生成 | ✅ biome_modifier JSON（数据驱动） | ✅ BiomeModifications API | ✅ |
| 村民、战斗、交易钩子 | ✅ 事件总线丰富，少用 Mixin | ⚠️ 更依赖 Mixin | ⚠️ 同左 |
| 真正的配置文件 | ✅ ModConfigSpec，内置服务端同步 | 需要第三方库 | 需要第三方库 |
| 引导书（Patchouli）/ JEI / Jade | ✅ | ✅ | ✅ |
| 命名体系 | Mojang 官方 + Parchment | Yarn（26.x 起要换） | Mojang 官方 |
| 目标玩家（冒险/神话内容整合包） | **主阵地** | 次要 | 很小 |

### 8.3 结论

- **选定 NeoForge + 1.21.1（Java 21，ModDevGradle），先只做单一加载器。**
  - 本项目是重内容的神话冒险模组，目标受众在内容向整合包。这个人群和同类竞品都集中在 NeoForge 1.21.1。
  - 圣物要用的 Curios、减少 Mixin 的事件体系、数据驱动的生物生成、原生配置，这几项需求 NeoForge 都匹配得更好。
  - NeoForge 本来就用 Mojang 官方命名，以后迁到 26.x 只是增量移植，不需要重写。
- **不选 26.x：** 内容向整合包几乎为零（NeoForge 66 个、Fabric 1,331 个，且以原版增强类为主），核心竞品也还没跟进。
- **暂不做双加载器：** 项目以往的主要失败模式就是范围膨胀。双加载器意味着适配层和测试都要做两遍。
  - 先把领域逻辑隔离到不依赖加载器的 `core` 包。
  - 希腊 alpha 发布后，根据反馈再决定是否用 Architectury 补 Fabric 版。
