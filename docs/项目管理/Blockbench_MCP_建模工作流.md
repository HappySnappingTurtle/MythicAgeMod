# Blockbench MCP 建模工作流

## 目的

减少“在同一个模型上反复试错、每次进游戏后才发现结构逻辑问题”的情况，把行走树这类实体建模改成一个有门槛、有检查点的流程。

## 第一优先级约束

WalkingTree 的总约束先看这里：

- [WalkingTree_明确约束与验收基线.md](./WalkingTree_明确约束与验收基线.md)

后续每一轮 WalkingTree 建模都必须先对照这份文档。
如果当前截图、运行时效果、局部设计想法和这份文档冲突，**以这份文档为准**。

## 当前问题总结

- 以前的流程里，`bbmodel`、运行时 Java 模型、游戏内观感三者经常不同步。
- 缺少“结构逻辑审计”，导致模型虽然能显示，但会出现：
  - 根没有真正连到树干
  - 主根和根须分层错位
  - 主根角度正确但视觉上仍像散开的零件
- 每轮修改的目标不够单一，经常把体量、连接、朝向、根须姿态混在一起改，难以判断哪一步真正起作用。

## 采用的社区思路

结合 Blockbench MCP 社区仓库和示例工程，这里采用下面几个原则：

1. **Query First**
   - 开始改模型前，先查看当前层级、贴图和截图，再动手。
2. **Hierarchy Before Geometry**
   - 先把模型拆成明确结构组，再补几何。
3. **Modeling / Texturing / Animation 分阶段**
   - 不在一次循环里同时改结构、贴图和动作。
4. **Screenshot Review Before Runtime**
   - 先做模型审计和截图审查，再进游戏验证。
5. **Independent Audit Before Runtime**
   - 每轮建模结束后，必须由独立 SubAgent 做一次客观逻辑审计，不能只靠建模者自己判断。

## 推荐工作流

### 阶段 0：冻结目标

每次迭代开始前，只允许定义 1 到 2 个目标，例如：

- “所有外圈主根必须通过连接根接到树干”
- “树干加粗，但根须姿态不动”

不要在一个回合里同时改：

- 体量
- 根的连接
- 根须姿态
- 树冠
- 贴图
- 动画

### 阶段 1：结构拆解

先把目标写成结构件清单，再开始动模型。

对于行走树，结构清单固定为：

- `trunk`
- `trunk_base`
- `root_flare`
- `root_crown`
- `inner_root_bundle`
- `buttress_roots`
- `major_roots`
- `secondary_roots`
- `hanging_roots`
- `attack_roots`

如果某次要新增结构，必须先说明它属于哪一层，而不是直接往模型里加零件。
尤其是攻击相关结构，必须明确写清楚：

- 它属于 `trunk`、`root_collar` 还是 `canopy underside`
- 它为什么在生物学/造型逻辑上成立
- 它不能只是“为了让游戏里看得见”而漂浮在树干上方

对当前 WalkingTree，攻击根的默认逻辑约束是：

- **作为前端较长根须，属于前侧根系层**
- 它们是“手”，但本质仍是根
- 不能从树干中段直接长出来
- 也不能从树冠下缘垂下来冒充手臂

对当前 WalkingTree，主支撑根的默认逻辑约束是：

- 必须至少有 **4 到 6 根可见主支撑根**
- 这些根属于下部根系层，而不是隐藏辅助腿
- 它们既要在 `bbmodel` 中作为主要结构存在，也要在 Java 模型动画里参与步态
- 不能出现“很多根负责造型，只有两条隐藏腿真正走路”的情况

### 阶段 2：Blockbench / Java 同步建模

建模时遵守两个规则：

1. **先改 `WalkingTreeModel.java` 的结构参数**
2. **再把完全相同的参数同步到 `walking_tree.bbmodel`**

优先使用：

```bash
python3 tools/sync_walking_tree_bbmodel.py
```

来重建 `bbmodel` 的关键元素参数和 outliner 层级，避免再出现：

- Java 已改，但 `bbmodel` 仍是旧层级
- 新增根部件没有 UUID
- `attack_roots` 没进 trunk 层级，导致审计和真实结构脱节

这样可以保证：

- Java 运行时模型是当前真值
- `bbmodel` 是唯一可回编源
- 二者不会各自漂移

### 阶段 3：单独模型审计

每次建模结束后，**禁止直接进游戏**，必须先跑：

```bash
python3 tools/audit_walking_tree_model.py
```

当前这份脚本至少检查：

- UV 是否越界
- 树干宽度是否达标
- 连接根数量是否足够
- 主根是否朝外
- 主根和根须是否上下分层
- 严格连通性是否成立
- 攻击根须长度是否足够可见
- 攻击根须是否起源于树干上半段，而不是树干/树冠上方
- 攻击根须最高点是否高于树干顶部
- 主支撑根数量是否达标
- 主支撑根是否全部朝外
- 主支撑根是否严格连到树干体系
- Java 动画里是否真的驱动了足够数量的可见主支撑根

如果审计失败，这一轮不进入游戏测试。

### 阶段 4：独立 SubAgent 审计

每次建模结束后，除了本地脚本，还必须再做一次**独立 SubAgent 审计**。

这不是建议，而是**硬门槛**：

- 没有独立 SubAgent 审计，这一轮建模不算完成
- SubAgent 审计没有明确通过，这一轮禁止启动游戏验证

要求固定为：

- SubAgent 只做审计，不参与本轮建模实现
- 审计输入至少包括：
  - 当前目标
  - 关键截图或用户反馈图
  - `WalkingTreeModel.java` 关键片段
  - `walking_tree.bbmodel`
  - 本地审计脚本输出
- 审计输出必须明确给出：
  - 是否符合结构逻辑
  - 哪些部件存在逻辑错误
  - 哪些审计规则还不够，必须补充

如果 SubAgent 给出明确逻辑失败，这一轮同样**不进入游戏测试**。

审计完成后，必须把结论落到独立记录中，例如：

- `docs/项目管理/WalkingTree_独立审计记录.md`

并且在进入游戏前再跑一遍门禁检查：

```bash
python3 tools/verify_walking_tree_model_gate.py
```

只有当这份记录存在、结论为 `PASS`，并且更新时间不早于当前 `WalkingTreeModel.java` / `walking_tree.bbmodel` 时，才允许继续。

### 阶段 5：Blockbench 视角审查与用户确认图

在进入游戏前，至少要从三个角度检查模型：

- 正面
- 45 度
- 侧面

并且先生成一张当前模型确认图发给用户，确认结构逻辑无误后，才允许继续进入游戏。

这一步的重点不是“好不好看”，而是结构是否讲得通：

- 树干是不是连续长到根部
- 外圈根是不是通过连接根过渡出去
- 根须是不是在最底层，而不是漂在中间
- 攻击根须是不是从前侧根系层长出，而不是从树干中段长出或从树冠下缘垂下来

### 阶段 6：编译与游戏验证

只有审计通过后，才执行：

```bash
./gradlew build --offline
./gradlew runClient --offline
```

游戏里只验证这一轮的单一目标，不顺带评价所有部分。

例如这一轮只验证：

- 是否所有根都接到了树干
- 树干是否够粗

不要在同一轮里又切回去评价树冠或贴图细节。

### 阶段 7：记录结论

每轮结束都要写清楚三件事：

- 审计通过了什么
- 游戏里暴露了什么
- 下一轮只收哪一个问题

## 适合当前项目的实际落地方式

对于 MythicAgeMod，这里采用下面的稳定流程：

1. 用户给目标和截图
2. 我先写本轮设计边界
3. 修改 `WalkingTreeModel.java`
4. 执行 `python3 tools/sync_walking_tree_bbmodel.py`
5. 跑 `tools/audit_walking_tree_model.py`
6. 启动独立 SubAgent 做客观审计
7. 先生成模型确认图给用户
8. 只有双重审计和用户确认都通过后再编译和启动游戏
9. 用户只反馈本轮目标是否达成

## 当前建议

对行走树下一轮开始，改用下面这个节奏：

1. 先只解决“**所有外圈根都必须通过连接根接上树干**”
2. 审计脚本必须把“严格未连接部件”列出来
3. 独立 SubAgent 不通过前不进游戏
4. 通过后再看贴图和根须姿态

## 结论

Blockbench MCP 社区仓库给我们的启发不是“已经有一个现成的 Minecraft 行走树工作流可以直接照搬”，而是：

- 把建模任务拆阶段
- 先查询当前模型状态
- 先做层级和结构，再做细节
- 用可重复的审计和截图代替纯人工猜测

真正适合这个项目的工作流，必须把 **Blockbench MCP 的分阶段思路** 和 **本地的结构审计脚本** 结合起来。
