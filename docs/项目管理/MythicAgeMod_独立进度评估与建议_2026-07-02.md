# MythicAgeMod 独立进度评估与建议

> 日期：2026-07-02
> 性质：独立第三方视角评估，不以既有设计文档的结论为前提。基于三路实地调查：设计文档体系、全部 Java 代码（246 文件）、资源与构建产物（含全量引用校验、编译验证、崩溃日志）。

---

## 一、一句话结论

**这是一个工程完成度远超普通业余 mod 的项目——代码骨架接近完整、可编译、可运行——但它现在最大的问题不是"还差多少内容"，而是三件事：① 对外声明（1.0 已发布）与内部审计（NOT_READY）互相矛盾；② 面向玩家的"手感层"（美术、掉落、合成、进度引导）系统性缺失；③ 验收体系的规模（446 场景、138 动作、30 生物人工签收）与实际产能不匹配，正在成为项目自己的阻断器。**

---

## 二、进度盘点：实际做到了什么

### 2.1 已落地（经代码与资源核实，非文档声称）

| 模块 | 实际状态 |
|---|---|
| 实体 | 43 个 EntityType 全部注册、全部有渲染器、30 个神话生物全部有生成规则（SpawnRestriction + BiomeModifications 各 30 次）。AI 是真实现：12 个自定义 Goal（冲锋、石化凝视、飞行、朝圣等），5 文明抽象基类被 28 个实体继承 |
| 神力/法术 | 56 个法术全部经 SpellRegistry 注册、全部有物品模型和纹理，均有真实 executeCast 效果（深度不一，详见 3.2） |
| 经济系统 | 3 个证书管理器（共 1100+ 行）真实实现五文明差异化产出，含 NBT 持久化读写 |
| 方块 | 10 个方块 + 6 个方块实体，雕像兑换、丰饶祭坛、招引塔均有真实 tick/交互逻辑 |
| 世界生成 | 5 文明村庄 jigsaw 结构全覆盖（structure×5、template_pool×5、structure_set 权重 25/20/20/15/15），15 个神殿 NBT 引用零缺失 |
| 资源 | 232 张纹理、312 个模型 JSON、164 个音效、13 种粒子、3 语言共 2300+ 词条。**全量脚本校验：模型 parent、textures、blockstate、结构池引用 0 缺失** |
| 构建 | `compileJava` 通过（exit 0），存在 2026-06-22 构建的 1.0.0 jar（35.8MB），最近一次 runClient 日志干净 |
| 代码卫生 | 全仓仅 5 处 TODO、0 处空 catch、Mixin 仅 2 个（克制）、分包清晰 |

这个底盘的含金量应当被承认：**"注册了但不刷/写了但没接线"的常见半成品病，本项目基本没有。**

### 2.2 未落地 / 有问题（同样经核实）

**功能性缺口：**
1. **圣物"三层效果"只实现了手持层。** 神殿层效果只存在于 tooltip 文本；`RelicPedestalBlockEntity` 的神殿结构检测是占位（实际只检测一块石砖平台），`RelicItem.java:340` 明确 TODO。玩家会读到 tooltip 承诺、发现不生效——这比没有这个功能更糟。
2. **数据包四大类全部为零：loot_tables、recipes、advancements、tags 一个都没有。** 掉落靠代码里的 `dropLoot` 硬编码，无合成配方，无进度树，无方块标签（意味着自定义方块可能用什么工具挖都一样/都不掉落）。
3. **语言文件三向不一致**：en_us 783 / zh_cn 816 / ja_jp 753 条，zh 独有 65 键（雕像交互提示英文玩家看不到）、en 独有 32 键（圣物效果描述中文玩家看不到）、ja 缺 48 键。
4. **一次真实并发崩溃**（2026-06-14）：`LegacyRandomSource` 多线程访问，栈在刷怪逻辑。这类崩溃在单人偶发、在服务器上会成为高频崩服点，未见修复记录。
5. 杂项：`fabric.mod.json` 引用的 `icon.png` 不存在；`structures/temple/greek/` 空目录残留；无任何测试代码（尽管有单元测试设计文档）。

**质量债：**
6. **新旧两套神殿守护者实体并存**（`TempleGuardianEntity` 732 行 + `CustomTempleGuardianEntity` 763 行，各带 5 文明变体，占用 11 个 EntityType），旧版疑似已被取代但未清理，且两套都还被注册和引用。
7. **118 处 `System.out.println`** 调试残留（项目有 SLF4J LOGGER 却没用上）。
8. 包名仍是 `com.example.mythic_age`——发布前必须改，越晚改重构成本越大。
9. Mixin 中用反射访问私有 goalSelector，跨版本脆弱。

**美术与验收缺口（引用项目自己的审计，经抽样属实）：**
10. 0/30 生物通过视觉签收，非希腊 20 生物为"工程首版/占位美术"；动作仅 30/168；0/52 神力人工 playtest；粒子多为原版组合。

### 2.3 进度的诚实读数

用项目自己的门禁口径：`ready_for_1_0 = false`，4 个 release blocker 未解除。用独立口径估算：

- **工程/代码层：约 85%**（缺圣物神殿层、守护者去重、崩溃修复、日志清理）
- **内容数据层：约 60%**（法术/实体全在，但 loot/recipe/advancement/tags 为 0，语言不同步）
- **美术/表现层：约 35-40%**（资源文件齐 ≠ 质量达标，这是项目审计自己反复强调的）
- **可发布成熟度：不足以称 1.0。** 当前状态更接近一个诚实的 **0.8-beta**。

**必须点名的问题：CHANGELOG 宣称 "1.0.0 已发布"、README 宣称"五文明可玩基础版"、`gradle.properties` 写着 `mod_version=1.0.0`，而仅早两天的内部审计明确判定 NOT_READY，且 CHANGELOG 里的 "Pegasus V4 / Hydra 9 头" 与审计记录的"仍是 V2、Hydra 硬编码 5 头"直接矛盾。** 无论原因是什么（乐观提交、文档先行），对外口径与事实脱节是发布前必须归零的信用问题——玩家和 mod 社区对"版本号说谎"的容忍度是零。

## 三、三个视角的评估与建议

### 3.1 MC Mod 开发者视角

**好的方面**：架构分层是教科书式的（entity/spell 按文明分包、抽象基类复用、Mixin 克制、注册中心集中）；SpellbookItem 从 4334 行重构到 170 行 + SpellRegistry 是正确的方向；NBT 持久化真实做了跨存档验证。

**建议（按优先级）：**

- **P0 修崩溃**：`LegacyRandomSource` 并发崩溃大概率来自自定义刷怪/AI 在非主线程碰 world random。全局审查所有 `world.getRandom()`/生成逻辑的线程上下文。这是唯一一个"会在玩家面前崩服"的已知问题。
- **P0 版本号回滚**：`mod_version` 改为 `0.9.0-beta`（或类似），CHANGELOG 的 1.0.0 条目改为 unreleased/候选。同时把 README 顶部与正文的矛盾清掉（正文还留着"四文明神力待实现"的旧口径）。
- **P1 补数据包四件套**：至少给 30 个生物做数据驱动 loot table（把硬编码 `dropLoot` 迁移过去）、给证书/圣物相关物品做 recipe 或明确"不可合成"的设计声明、做一条最小 advancement 引导链（见 3.2）、给自定义方块补 mineable tags。这四类是 MC mod 的"及格线基建"，也是兼容其他 mod（数据包可覆盖）的前提。
- **P1 删旧守护者**：两套 763/732 行的守护者实体是最大单项技术债。确认新版覆盖旧版功能后删除旧版及其 5 个变体注册（注意存档迁移：旧实体 ID 需要 DFU 处理或明确弃档声明——beta 阶段是弃档成本最低的时机，越拖越贵）。
- **P1 日志治理**：118 处 System.out 一次性脚本迁移到 LOGGER，发布版噪音归零。
- **P2 包名**：`com.example` → 正式域名倒写，趁 beta 改。
- **P2 依赖升级**：fabric-loader 0.14.21 / API 0.83.0 是 1.20.1 早期版本，升到 1.20.1 线的最新（loader 0.15+/API 0.92+）能白捡两年的修复。
- **P2 最小测试**：不必追求单测覆盖，用 Fabric GameTest 写 3-5 个冒烟测试（实体能生成、法术能施放不崩、证书能产出）挂在 build 里，比 446 个人工场景现实得多。

### 3.2 玩家视角

假设我是一个从 Modrinth 下载了这个 mod 的普通玩家：

**会被打动的**：五文明村庄探索 + 各文明完全不同的证书获取方式（希腊挖矿兑换 / 埃及神像挂机产出 / 北欧打怪掉落 / 中华养村民 / 亚特兰蒂斯海晶交易）——这个差异化经济设计是真正有创意的，市面上神话类 mod（Ice and Fire、Mythic Mobs 系）没有这个维度。守护者交易 GUI、引导书（383 行的 GodPowerGuideItem）说明作者想过引导问题。

**会流失我的**：
1. **进游戏后不知道干什么。** 没有 advancement，意味着按 L 键什么都没有；没有配方，意味着 JEI/REI 里查不到任何入口。一个内容量 56 法术 + 30 生物的 mod，玩家的第一小时体验完全依赖"恰好走到一个村庄且恰好右键了守护者"。**建议：一条 8-12 节点的进度链（发现村庄→拿到第一张证书→兑换第一本法术书→施放→找到圣物→…），比再加 10 个法术的价值高一个数量级。**
2. **美术会让我在截图阶段就关掉页面。** 项目自己的审计说非希腊 20 生物是占位美术、纹理"像程序生成"。mod 的下载转化几乎完全由页面截图决定——这是发布层面真正的 P0。
3. **承诺了但不生效的功能**（圣物神殿层 tooltip）会直接产生差评和 issue。要么接线，要么先从 tooltip 里删掉。
4. **18 个高风险世界编辑法术**（陨石雨、洪水、地震、诸神黄昏……）没有防护配置的话，任何服务器都不敢装。**建议：ModConfig 里给破坏性法术加总开关 + 破坏保护白名单（已有 ModConfig 类，是接线而非新建）。**
5. **平衡感知**：部分法术明显轻量（仙鹤祈福=召唤 2 只灰鹦鹉+buff）与深度法术（行走的森林 305 行）放在同一价位体系里，玩家会很快识别出"哪些法术是凑数的"。宁可 1.0 砍到每文明 6-8 个精品，也别 10 个里有 3 个一次性体验。

### 3.3 产品/创意视角

**定位判断**：「AoM 五文明 × MC 生存」是一个有清晰差异化的定位。市场上生物类 mod 饱和，但"文明经济系统 + 神力施放"作为组合是空白。**项目的核心资产不是 30 个生物，而是证书经济循环——这点在对外宣传上应该反转过来（现在 README 把生物列在最前面）。**

**独立判断与建议：**

1. **发布策略：放弃"五文明齐步走 1.0"，改为垂直切片先行。** 内部文档的 W1 阶段（希腊 vertical slice）方向是对的，但结论应该更激进：**把打磨好的希腊单文明作为 0.9 公开 beta 发上 Modrinth/CurseForge**，其余四文明标注 experimental 或分版本推出。理由：(a) 30 生物 × 视觉签收 + 446 playtest 场景的全量门禁，以当前产能可能永远到不了 1.0；(b) 早期玩家反馈会重排你的优先级（大概率玩家会指向引导和平衡，而不是文档关注的动作帧数）；(c) mod 社区对"持续更新的 beta"的善意远高于"憋大招后的平庸 1.0"。
2. **验收体系需要右移尺寸（right-size）。** 现有门禁体系（12 需求项、10 模块矩阵、审计脚本、生产锁）作为工程纪律非常出色，但它是按团队产能设计的。446 个人工 playtest 场景、138 个动作捕获、1020 帧动画预算，对单人项目是自我阻断。**建议把门禁分为两级：发布门禁（崩溃/存档安全/经济闭环跑通/每文明 1 个代表生物达标）和质量愿景（其余全部转为版本路线图）。**
3. **IP 风险要有一页纸的结论。** 神话本身是公有领域，但项目公开定位是"基于微软《Age of Mythology: Retold》"。建议：宣传文案改为"inspired by mythology / AoM-like"，不使用 AoM 的商标性表述、不复刻其美术与音频资产、mod 页面加非官方声明。目前所有内容（生物名、神力名）都是通用神话概念，实质风险低，但"基于微软 XX 游戏"这个表述本身要改。
4. **版本窗口**：1.20.1 在 2026 年仍是模组存量最大的版本之一，作为首发是合理的；但应在路线图里明确 1.21.x 移植计划，否则新玩家占比会逐季流失。
5. **文档体系**：19 个月、几十份文档、单一 git commit——文档密度远超代码提交密度。建议 (a) 建立真实的 git 提交习惯（当前无法回溯任何演进历史，audit 只能靠文档自述）；(b) 把"当前唯一可信"的 2026-06 审计口径固化为一份 `STATUS.md`，其余全部移入 archive，`_备份` 副本删除。README/CHANGELOG 这类对外文件今后只从审计结果生成，杜绝再次脱节。
